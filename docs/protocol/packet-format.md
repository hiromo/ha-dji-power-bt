# Packet and record formats

## DUM-like frame

The BLE application protocol uses a DJI DUM-like frame.

**Confirmed current parser/builder layout**

```text
offset  size  field
0       1     sync = 0x55
1       2     length/version packed little-endian
3       1     DJI header CRC8 over bytes 0..2
4       1     sender
5       1     receiver
6       2     sequence, little-endian
8       1     command type
9       1     command set
10      1     command ID
11      N     payload
-2      2     DJI CRC16 over all preceding frame bytes
```

Minimum frame length is 13 bytes. The encoded length is 10 bits and must not exceed `0x03FF`.

## Transport protocol version field

**Confirmed structural interpretation; observed value is currently 1**

The packed length/version word is decoded as:

```python
length  = raw[1] | ((raw[2] & 0x03) << 8)
version = raw[2] >> 2
```

The builder currently emits:

```python
length_version = length | 0x0400
```

which means version `1`.

Treat this as the DUM transport protocol version. The integration currently parses it into `DumlFrame.version` but does not yet aggregate it into runtime diagnostics. If diagnostics are added, record versions observed rather than assuming all future frames remain version 1.

Do not confuse this transport version with unresolved application/product revision fields inside configuration record `0x1000`; see `unknowns.md`.

## CRC algorithms

Header CRC8:

- initial value `0x77`
- reflected polynomial operation using `0x8C`

Frame CRC16:

- initial value `0x3692`
- reflected polynomial operation using `0x8408`

Use the existing implementation and captured-frame tests rather than replacing it with a generic named CRC variant based only on a label.

## Generic TLV scanning

Many payloads contain little-endian 16-bit ID and 16-bit length records:

```text
u16le id
u16le length
length bytes value
```

The integration provides scanning helpers because some payloads include outer headers before the first useful record.

For nested tables that are written back (`0x100D`, `0x101E`), parsing is stricter: records must form a complete contiguous table of the expected nested record ID. Any unexpected nested ID, malformed length, or tail is retained as unparsed diagnostic hex and disables write-back.

## Common 16-byte keyed header

Configuration writes and observed 0x66 reports use a common-looking 16-byte prefix. Current write construction uses a keyed header beginning with:

```text
00 00 10 00
```

followed by timestamp/session material generated by the existing builder.

Do not interpret the recurring `0x10` byte as an application protocol sub-version without new evidence. Current evidence fits a record/header marker at least as well as a version field.

## 0x66 provisional HMS body

**Observed and intentionally provisional**

When the payload begins with the common 16-byte keyed header, `0x66` parsing removes that header and treats the remaining body as:

```text
u16le metadata_raw
u16le declared_record_count
repeat declared_record_count times:
    u32le alarm_id
    u8    sensor_index
    u8    report_level
    u16le reserved
```

An empty report body is:

```text
00 00 00 00
```

The parser accepts the structure only when the body length exactly equals:

```text
4 + record_count * 8
```

Otherwise the report is `unrecognized`; it is not partially decoded.

The semantics of alarm IDs, sensor indexes, and report levels remain reverse-engineered. See `telemetry.md` and `unknowns.md`.

## Configuration record 0x1000

`0x1000` contains at least firmware strings shared by Power 2000 and Power 1000 Mini:

- bytes `[7:23]`: station/main firmware ASCII, NUL terminated;
- bytes `[24:40]`: communication-module firmware ASCII, NUL terminated.

Other fields in this record are intentionally not assigned production semantics yet. Several are strong product/revision/capability candidates; see `unknowns.md`.
